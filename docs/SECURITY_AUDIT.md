# Antigas security audit

**Snapshot:** 2026-09-29
**Branch:** `security-hardening`
**Method:** source/configuration review, repository/history secret-pattern scan, static parsing, unit tests, and local .NET builds. No production connection, deployment, destructive probe, or public attack simulation was performed.

**Finding totals:** 0 confirmed P0; 0 confirmed unconditional P1; 1 conditional P1; 4 open P2; 1 open P3. Fixed items are listed separately and are not counted as open findings. These are findings from source review, not a claim that the live server has been penetration-tested.

## Inventory and architecture map

The current tracked repository contains 1,705 files: 80 C++ sources, 87 C++ headers, one C source, 748 Lua scripts, 246 XML files, 337 NPC files, 39 `.ndb` data files, 35 JSON files, 3 SQL files, 27 Python files, 3 Shell scripts, 6 PHP files, 7 C# sources, CMake files, and client/server data assets. No Makefile, Dockerfile, submodule, or GitHub Actions workflow existed at the start of this audit. `config.lua` is intentionally ignored.

| Component | Purpose / entry points | Risk / criticality | Dependencies / evidence |
|---|---|---|---|
| C++ game server (`src/`) | Boost.Asio listeners, protocol parsers, game loop, players/items/creatures, scheduler/dispatcher, Lua bindings, MySQL persistence and save/shutdown. | Critical: remote packets, process lifetime, mutable world state and economy. | C++11, CMake 3.16+, Boost system/filesystem, LuaJIT, PugiXML, MySQL/MariaDB client, GMP, pthreads. |
| Lua (`data/`) | NPCs, monsters, actions, spells, movements, creaturescripts, talkactions, globalevents, startup/shutdown and custom Market/rarity features. | High: remote actions and callbacks can mutate player/world/database state; script errors/loops affect server. | LuaJIT 5.1 API and C++ bindings; 748 tracked `.lua` files. |
| Persistence (`src/database.*`, Lua `db.*`, `data/sql/`) | Login, player/world saves and Market tables/migrations. | Critical: account access, item/money integrity, availability and recovery. | Single MySQL client connection in core; three tracked Market SQL files; base schema is not in this repository. |
| Network/protocol (`src/server.cpp`, `connection.cpp`, `protocol*.cpp`, `networkmessage.*`) | TCP accept, login/game/status protocols, packet parsing and output queues. | Critical: every Internet-reachable game/login port is an untrusted boundary. | Boost.Asio; fixed packet buffer and protocol-specific parsers. |

The repository does not contain the production systemd unit or an authoritative startup script, so actual service user, restart policy, limits, ports and shutdown ordering cannot be confirmed from this checkout.

Packet throttling is per socket; `maxPlayers` is reached later. Each socket carries fixed buffers/timers and outgoing messages queue in a list. | DOS-03 · P2 · Fixed in this branch · src/protocolstatus.cpp, src/statusqueryratelimiter.h · ProtocolStatus::onRecvFirstMessage | Each distinct non-local IP that queried the status protocol (default port 7171, timeout 5000 ms) was retained in a static map for the process lifetime, although the entry only affected the next five seconds. ## Positive controls observed

- Packet length is bounded before body reads (`src/connection.cpp:157`); game protocol parsing checks the declared cursor boundary (`src/protocolgame.cpp:469`). The inspected auto-walk parser checks the requested direction count against remaining packet data before skipping it.
- NetworkMessage now rejects negative/out-of-range cursor advances and guards reverse reads. The only tracked reverse-read caller is auto-walk, which also validates its direction count before seeking.
- OTCv8 new-walking parsing now checks the inner packet length and refuses to dispatch an empty direction list before its callback can inspect the first step.
- Message-driven game tasks are now gated on the parser cursor remaining inside the declared packet and physical buffer; login and manual dispatcher paths use the same validity check.
- Failed or cancelled accept callbacks now release the pre-registered connection, avoiding a retained `ConnectionManager` entry during service shutdown/retry.
- The launcher release path uses a fixed HTTPS origin, signed ECDSA manifest, SHA-256 package comparison, archive size/count limits, path traversal/collision checks, symlink rejection, and rollback logic (`deploy` C# launcher sources). The launcher and signer compiled successfully with the available .NET SDK.
- Public account/order queries in the inspected PHP sources use PDO prepared statements; registration constrains account/name/password inputs and places account/character creation in a transaction. Private middleware remains out of scope.
- `config.lua` is ignored and not tracked. It was inspected only for safe properties; no values were printed or copied into this report. It uses a non-root DB user and loopback host in this local checkout. This does not establish production configuration.
- A custom limited-pattern scan of 1,675 historical/current text blobs found no matching private-key/token/credential patterns. Gitleaks 8.30.1 also scanned the Git history locally (archive depth 2) and reported zero findings. Neither local scan checks provider-side secrets or proves that secrets were never exposed outside this repository.
- A targeted scan found 12 `addEvent` call sites across the tracked Lua scripts. Review of their timer arguments found no direct `Player`/`Creature`/`Item` userdata passed to callbacks; the identity-bearing cases use numeric IDs, while the other reviewed values are primitive or Lua data tables. `luaAddEvent` only normalizes recognized userdata at the top level, so nested-table safety still depends on each call site. This was a source review, not a LuaJIT runtime lifecycle test.
- `Container::queryAdd` walks ancestors to reject insertion cycles but has no nesting-depth ceiling. The Market's former recursive backpack walk therefore accepted a client-influenced structure whose recursion depth was not bounded. It now traverses iteratively and stops after 10,000 nodes; this bounds Market scan work, not nesting or traversal in other engine subsystems.
- The status protocol previously retained each remote source IP indefinitely in process-global state despite a configured five-second duplicate-query window. The local IP limiter now expires entries using a steady clock; the status port's production exposure still needs firewall verification.
- data/globalevents/lib/lamp_states.lua is persisted table data, not an executable Lua chunk: its loader prepends return. CI syntax validation parses a temporary return-plus-table wrapper and never evaluates the persisted data.

## Validation and limitations

- Python unit tests: 14 passed across load-test parsing, staging safety, and recovery behavior. These tests do not exercise the Market inventory scan.
- Three local self-tests passed; all seven mutating probes refused execution when staging approval was absent. Bestiary and Quest Log imported without invoking DB/network operations.
- All five legacy deployment scripts refused a phase without the explicit production flag. Both Nginx scripts passed `bash -n` and refused execution without their production-change flag.
- XML: 246/246 files parsed. Python AST parsing: all 27 Python files parsed.
- C# launcher and ReleaseSigner: `dotnet build --no-restore`, 0 warnings and 0 errors each.
- New CI uses pinned GitHub Actions SHAs, read-only default permissions, separate TSan from ASan/UBSan, and a separate release-hardened mode. The pinned refs resolve to actions/checkout v7.0.1, CodeQL Action v4.38.2, and Gitleaks Action v3.0.0; these current refs use Node 24, avoiding GitHub's September 2026 removal of Node 20. CodeQL uses its supported `none` build mode for C++/C#. All three GitHub Actions workflow files pass actionlint 1.7.12 locally, and Gitleaks 8.30.1 reports zero findings over local Git history with nested-archive depth 2. The hosted workflows have not run because this checkout is local and has no GitHub runner attached. If the repository belongs to a GitHub organization, its owner must add the Gitleaks license secret before the secret-scan job can run; personal repositories do not require it.
- luaparse 0.3.1, integrity-checked from npm, parsed all 748 tracked Lua paths in LuaJIT mode; lamp_states.lua was parsed as a table expression. This is syntax coverage, not native LuaJIT bytecode compilation. A targeted Gitleaks 8.30.1 scan of the updated workflow reported no leaks. A fresh whole-directory scan encountered untracked .NET Brotli DLL build artifacts and was stopped; the prior full-history and working-tree scan passed before this workflow edit.
- The standalone status-IP cache regression test compiled with the installed MSVC toolchain and passed 20 consecutive runs. It covers the configured timeout boundary, eviction of 10,000 expired IPs, zero/negative timeout behavior and concurrent insertion. This does not build or link the full Linux-only server.
- Full server build, sanitizer/fuzzer runs, native LuaJIT bytecode compilation, Lua/PHP lint, and deployment-tool validation remain unavailable locally: this Linux/PkgConfig CMake project lacks a local CMake/PkgConfig server dependency toolchain, LuaJIT, PHP, cppcheck and ShellCheck; the Docker Linux daemon is not running. The isolated status-cache C++ test did compile with MSVC, but that is not evidence that the server links. Both Nginx scripts passed Bash syntax checks through Git for Windows. No production/staging services were reachable or used.
- Cppcheck was not executed. Its official Windows release was offered as an MSI; automatic command review blocked invoking Windows Installer to extract it into an isolated temporary directory, so no installation was performed. CodeQL remains the configured C++ static-analysis workflow, but its hosted result is pending.
- GitHub Actions/branch settings, server firewall, production DB roles, systemd restart/limits, TLS renewal, private web/payment code, and live client update delivery need verification by an operator with access to those systems.

## Prioritized follow-up

1. Run the new workflows on GitHub; fix build/test issues, and make CI/security checks required in branch protection.
2. Measure unauthenticated connection occupancy and legitimate peaks; then design global/per-IP admission and queue limits.
3. Add controlled scheduler cancellation/memory tests and review dispatcher exception semantics plus process supervision.
4. Design compatible password-hash migration; parameterize SQL incrementally and explicitly set DB charset.
5. Add a parser-focused libFuzzer harness only after a standalone entry point can be isolated, then run ASan/UBSan corpus regressions in CI.
6. Review private web/Pix code, production firewall/service/database configuration, release signing-key custody, GitHub settings, backups and restore procedure.
